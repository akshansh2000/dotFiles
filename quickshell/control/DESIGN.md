# Control centre - design

Status: APPROVED by the user 2026-11-13. Nothing here is built yet; a throwaway
spike exists at `/tmp/claude-1000/spike/`.

Name: **Control centre**. In code and commands it is `control`:
`quickshell/control/`, `qs ipc call control toggle`.

Calls marked **[my call]** were made by Claude, not the user. Check them.

## 1. Intent: why this exists

This Void Linux + river setup was built over two months, mostly in agent
sessions. The knowledge of what is where, why each choice was made and how
the pieces fit now lives in three scattered places:

- code comments;
- commit messages;
- the agent's private memory files.

None of that is in the owner's head. The trigger was small: on 2026-11-06 the
user couldn't remember where the logs were.

The control centre is a desktop app to **see** the system and **change** it:

- **see:** where everything is, why it is that way, how it works;
- **change:** through the scripts that already exist.

The user is also building it for fun, and wants to make the design choices.

What success looks like:

- any "where is / why is / how does" question about this system is answered
  in the app within seconds;
- the app makes common changes without the user opening a file;
- the system stays fully text-first. Everything still works, and stays
  understandable, from a terminal without the app.

## 2. Goals, non-goals, anti-goals

### Goals

- Three panels:
  - **left:** sections;
  - **centre:** that section's controls;
  - **right:** that section's documentation and its files.
- One Markdown doc per topic, readable anywhere: the app, an editor, GitHub.
- As little hardcoding as possible. Topics, their files and their controls
  are discovered by convention.
- Keyboard-first throughout.
- The app documents itself, including its shortcuts.
- Eventually it covers every section of the system (list in §6).

### Non-goals

- Replacing the config files. They stay the source of truth, and the app
  stores no settings database of its own.
- A general-purpose settings app for other people's machines.
- A full Markdown editor. Docs are edited in a real editor; the one in-app
  write is the quick note (§7).

### Anti-goals: a failure even if it technically works

- The app becomes the only way to understand or change something.
- Changes happen that the user can't see. Every action shows the exact
  command it runs.
- It hardcodes lists of topics, folders or files in QML.
- It breaks the always-running Quickshell OSD.
- Docs drift silently out of date. The app must surface drift (§7).

## 3. Constraints

- Void Linux, runit (no systemd). User services live in
  `~/.config/sv` (= `~/.local/sv`).
- **Quickshell 0.3.2** (Qt 6.11), already running as `sv/quickshell` with:
  - `quickshell/shell.qml`;
  - `Theme.qml`, generated by `theme/apply-theme.sh` from `Theme.qml.tmpl`;
  - `services/`: Audio, Brightness, KbdBacklight;
  - `osd/`.

  The app joins this same shell (§4.1).
- **New package: `inotify-tools`** (87 KB, no dependencies) for
  `inotifywait`. Add it to `system/packages.txt`.
- Python 3 stdlib only. **There is no PyYAML**, so the front matter is a
  deliberately small YAML subset (§5).
- The repo is **public** (github akshansh2000/dotFiles). Docs must never
  contain secrets.
- Private Use Area icon glyphs are written as
  `String.fromCodePoint(0x…)`, never as literal characters (see AGENTS.md).
- The user's working agreement (AGENTS.md) applies to building it:
  - discuss before changing;
  - test in isolation;
  - commit only when asked.
- Theme: Catppuccin Mocha via `Theme.qml`. Qt's default control style must
  not show; every control gets a custom Mocha style.

## 4. Architecture

### 4.1 Where it runs (user: same shell)

The app is part of the existing shell, inside a `LazyLoader`, so it costs
nothing until it is first opened.

- **Pros:**
  - It shares `services/` with the OSD: one PipeWire connection, one
    brightness watcher.
  - No second Qt process (~85 MB).
- **Risk:** an app bug affecting the OSD. Mitigations:
  - the app's QML loads lazily, so a runtime error in it doesn't stop
    the OSD;
  - **[my call]** development happens in a separate test instance
    (`quickshell -p <worktree>/shell.qml`) and only reaches the live shell
    once it works.

The alternative was a separate Quickshell config and process:

- **pros:** full isolation;
- **cons:** two processes, and `services/` has to be shared by symlink.

The user chose the same shell.

**As built (2026-11-13):**
- `shell.qml` loads the window with a `LazyLoader` from a plain `file://`
  URL. It does not import `qs.control`.
- Importing it was tried first: one typo in `control/` made the whole shell
  fail to load, OSD included.
- Under a `qs:@/` URL the folder's own types weren't found, because
  Quickshell only lists folders that imports reach.
- That's why control files use `import "."` / `import "widgets"`.
- The cost: no hot reload for `control/`, so restart the shell after
  editing.

### 4.2 Files

```
~/.config/
  docs/                          topic docs: every docs/*.md is a section
    control-centre.md            the app's own topic (self-documentation)
    audio.md, power.md, ...
  <any folder>/NOTES.md          optional folder notes (§5.3)
  quickshell/
    shell.qml                    + a LazyLoader for the app, + IpcHandler
    services/
      Topics.qml                 singleton: runs topics.py, exposes topics
      ...existing Audio/Brightness/KbdBacklight
    control/
      DESIGN.md                  this document (not a topic: not in docs/)
      ControlCentre.qml          the window and its three panels
      topics.py                  front matter -> JSON (stdlib)
      KeyMap.qml                 the key table (handling AND the ? overlay); not Keys.qml, which would shadow QtQuick's Keys
      widgets/                   Mocha-styled Slider, Button, Toggle, List...
      sections/<Id>.qml          optional controls per topic (§5.4)
  system/
    usr/local/libexec/...        root helper (staged; §8)
    etc/polkit-1/rules.d/...     its polkit rule (staged; see §8)
```

### 4.3 Data flow

1. `Topics.qml` runs `python3 -I quickshell/control/topics.py ~/.config/docs`.
2. topics.py prints a JSON array with one object per topic: `id`, `title`,
   `order`, `icon`, `groups`, `checks` and `body`. Each path entry is
   resolved to a full path, a detected `kind`
   (folder/script/doc/file/missing), and its folder's NOTES.md if one
   exists.
3. **Live reload (user's call).** `Topics.qml` runs
   `inotifywait -m -q -e close_write,create,delete,moved_to,moved_from
   ~/.config/docs` as a long-running `Process`. Any event re-runs topics.py
   after a short debounce of about 200 ms, since editors write files in
   several steps.
   - **[my call]** Only the docs folder is watched. Folder `NOTES.md` files
     and the `kind`/missing state of listed paths are refreshed when the
     window opens and on `r`. Watching every listed path would be hundreds
     of watches for little gain.
   - If `inotifywait` exits, it is restarted after 1 s, the same pattern as
     `Brightness.qml`'s `udevadm monitor`.
4. Live state (service status, battery, ...) comes from `services/`
   singletons or short `Process` calls. Nothing is polled while the window
   is closed.

## 5. Conventions: how nothing gets hardcoded

### 5.1 Topic = `docs/<id>.md`

- The file name is the id.
- Only top-level `docs/*.md` count, so subfolders can hold images etc.

### 5.2 Front matter schema

```yaml
---
title: Audio                 # shown in the left panel
order: 2                     # sort key; ties sort by title
icon: F057E                  # optional MDI codepoint (hex), drawn from Symbols Nerd Font
paths:                       # groups BY ROLE; names are free-form, shown in written order
  config:
    - wireplumber/           # relative to ~/.config ...
  services:
    - sv/wireplumber/
  keys:
    - path: river/keybindings.conf
      note: the volume / mic block      # optional
  logs:
    - /tmp/runsvdir-user.log            # ... or absolute / ~-prefixed
checks:                      # optional, for the Overview health panel (§7, idea 12)
  - sv: wireplumber
  - path: /run/asus-kbd-backlight
---
Markdown body...
```

- **Usual group names**, documented in `control-centre.md` (not enforced):
  config, services, scripts, ui, keys, logs, system.
- **The parser accepts exactly this shape:**
  - scalars at top level;
  - `paths:` → group name → list of strings or `path`/`note` maps;
  - `checks:` → list of one-key maps.
- **Anything else is reported as a parse error, not ignored silently.** The
  topic then shows a red error line, so a typo is visible.

### 5.3 Folder notes

- A `NOTES.md` inside any folder is shown in the right panel, under the
  topic doc, for every topic that lists that folder or a file inside it.
- That's how folder-specific exceptions surface without a registry.

### 5.4 Controls

- A topic gets controls if `quickshell/control/sections/<Id>.qml` exists.
  `<Id>` is the id in PascalCase: `audio` → `Audio`, `login-logs` →
  `LoginLogs`.
- Otherwise the centre shows the topic's file groups as an action list, so
  every section is useful from day one.
- **[my call]** The app finds out which section files exist with one
  `ls` via topics.py, so QML holds no list of them.

### 5.5 Writing a topic's body (added 2026-11-13, with the right-panel redesign)

The right panel isn't one Markdown text. `topics.py` (`structure()`) splits
the body into blocks, and `DocPanel.qml` draws each kind differently. Every
convention is optional; a body that uses none is shown as a single summary.

| In the Markdown | On the panel |
|---|---|
| text before the first `##` | **summary**, larger and softer (an H1 equal to the title is dropped) |
| `## At a glance` with `- Key: value` lines | **fact table** |
| `## Known issues` | its callouts on their own, at the end |
| any other `## Area` | a **card**: bullet points, callouts, commands, text |
| `> [!IMPORTANT]` | **WHY** (a decision), mauve |
| `> [!WARNING]` / `> [!CAUTION]` | red / peach |
| `> [!TIP]` / `> [!NOTE]` | green / blue |
| a ```` ```sh ```` fence | one copyable command row per line |
| `` `name` `` matching a listed path (or its unique basename) | a link that opens it |

GitHub renders the same file sensibly: the alerts are GitHub's own syntax.

**Writing rules:**
- about 200 words per doc;
- a summary of at most 2 sentences;
- at most about 4 areas, each with short bullets, not prose;
- write facts, decisions and gotchas, not descriptions of the controls on
  screen;
- refer to listed files by name in backticks, so they become links;
- put each command in its own `sh` block.

Example:

```markdown
---
title: Audio
order: 2
icon: F057E
paths:
  config:
    - wireplumber/
  keys:
    - path: river/keybindings.conf
      note: Volume / brightness / media keys (normal + locked, per river's own docs)
checks:
  - sv: wireplumber
---
PipeWire with WirePlumber, as runit user services.

## At a glance
- Output: Laptop Speakers

## Device names
- `wireplumber/` renames the built-in devices
> [!CAUTION]
> WirePlumber saves volume with a delay: wait before restarting it.
```

## 7. Features

### Core (version 1)

- **The three panels** as in the spike, with the right panel's readable
  spacing.
- **Keys:**
  - `j`/`k`/arrows: move between sections;
  - number keys: jump to a section;
  - Tab: move focus between panels;
  - `r`: reload;
  - `q`/Esc: close;
  - `?`: shortcuts overlay, generated from `KeyMap.qml`, the same table
    that handles the keys.
- **Self-documentation:** `docs/control-centre.md` is a normal topic. It
  lists the app's files and covers:
  - how the app works;
  - how to add a topic or controls;
  - the usual group names;
  - tips.

### The user's top picks, in the order they gave them

1. **`/` search (idea 1).** Fuzzy search over section titles, every path,
   doc text, and keybindings. A hit jumps to the topic with the hit
   highlighted.
2. **Theme playground (idea 8).** Swatches from `colors.sh`; edit one,
   preview it inside the app, then run `apply-theme.sh`.
3. **Richer audio (idea 10).** Per-app stream volume (PipeWire streams), and
   a live mic level meter (`PwNodePeakMonitor`).
4. **Overview health panel (idea 12).** Rolls up every topic's `checks:`.
   This is the rice-check idea; it feeds the waybar dot later.
5. **Live state on entries (idea 7).**
   - Service entries show a running/down dot and uptime, with restart and
     view log.
   - Missing paths show red.
6. **Quick note into a topic (idea 15).** Appends a dated line under a
   `## Notes` heading in the topic's doc, which the user commits as usual.
7. **"Ask Claude about this" (idea 16).** Opens foot with `claude` and the
   topic doc plus its paths as context.
8. **Keybinding cheat-sheet (idea 6).**
   - Per topic, the bindings from `keybindings.conf` in the blocks its
     `keys` entries name. **[my call]** A `keys` entry's `note` holds the
     exact `## ` block heading from `keybindings.conf` (e.g.
     `note: Volume / brightness / media keys`), so the link is plain text,
     not code.
   - The Keybindings section adds search, plus "press a key, see what
     it does".

### Kept for later, all wanted eventually

- **Idea 3:** open from outside via IPC: `qs ipc call control open <id>`

- **Idea 4:** a History tab per topic (`git log` on its paths).
- **Idea 5:** a stale-doc warning.
- **Idea 9:** wallpaper studio ("Mocha-ify" with A/B/C preview).

## 8. Root operations

- **How it works:**
  - the app runs `pkexec /usr/local/libexec/control-centre-helper <action> <arg>`;
  - the helper is a short root-owned script with a **fixed allow-list**
    (`charge-limit 60..100`, `power-profile quiet|balanced|performance`, …),
    and it validates its arguments.
- **The polkit part** (corrected during planning, 2026-11-13):
  - polkit reads `.policy` files only from `/usr/share/polkit-1/actions`,
    so there is no policy file;
  - pkexec's built-in `org.freedesktop.policykit.exec` action already asks
    for the admin password;
  - a rule in `/etc/polkit-1/rules.d/50-control-centre.rules` upgrades it
    to `auth_admin_keep` for this one program only;
  - the existing polkit agent (`sv/polkit-agent`) shows the password
    dialog.
- **Installation:** both files are staged under `system/` (`install.sh` gains
  `usr/local/libexec/` support); the user installs them with sudo.
- **Charge limit at boot:** the limit resets on reboot, so the helper also
  writes it to `/etc/control-centre/charge-limit`, and `/etc/rc.local`
  re-applies it at boot.

## 9. Opening the app

- **Window:** a regular window (`FloatingWindow`, app-id `org.quickshell`).
  It **tiles like any window**, so in the default monocle layout it's full
  screen. A float rule at 1200×760 was built and dropped the same day
  (2026-11-13, the user's call): too cramped, and monocle already gives it
  the whole screen.
- **Opening it:** an `IpcHandler` named `control` with `toggle` and
  `open <id>`.
- **Key (user's call):** the **Armoury Crate button** (`XF86Launch1`, which
  sends `KEY_PROG1`) runs `qs ipc call control toggle`. It's added through
  `river/keybindings.conf` + `gen-keybindings.sh --apply`, never by editing
  `river/init`.

## 10. Testing

- **topics.py:** run against sample docs, including broken front matter.
  It must report errors, not crash.
- **UI:** in a separate test instance (`quickshell -p …`), and screenshot
  with `grim`.
- **Root helper:** test its argument validation without pkexec first, then
  once through pkexec.
- **The OSD:** confirm it still works after the app is wired into the live
  shell.

## 11. Decisions (user, 2026-11-13)

1. **Process:** the same Quickshell shell as the OSD, lazily loaded.
2. **Name:** Control centre / `control`.
3. **Key:** the Armoury Crate button.
4. **Live reload:** use `inotifywait` (install `inotify-tools`).

The user accepted all the **[my call]** items as written.
